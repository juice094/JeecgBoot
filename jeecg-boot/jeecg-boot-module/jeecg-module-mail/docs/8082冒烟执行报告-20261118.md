## 1. 启动期发现并修复的缺陷（2 个，均为真实缺陷）

### D-1 MailPasswordCodec 无 bean，启动失败

- 现象：`APPLICATION FAILED TO START`，`Field passwordCodec in MailSyncEngine required a bean of type MailPasswordCodec that could not be found`
- 根因：`@ConditionalOnMissingBean` 直接标在 `@Component` 扫描类 `AesMailPasswordCodec` 上。Spring Boot 明确警告该注解只应在 `@Configuration` 的 `@Bean` 方法上使用——条件评估早于组件扫描注册，导致自身被跳过。
- 修复：抽出 `MailCodecConfig`（`@Configuration`），以 `@Bean + @ConditionalOnMissingBean` 声明；`AesMailPasswordCodec` 去掉 `@Component/@ConditionalOnMissingBean/@Value`，构造器改收纯参数。可插拔语义保留。
- 验证：单测 93/93 绿；启动成功。

### D-2 system-start 解析不到 mail 依赖

- 现象：`Could not find artifact org.jeecgframework.boot3:jeecg-module-mail:jar:3.9.6`
- 根因：`SKIP_AM=1` 跳过 `-am`，mail 模块未 install 到本地仓库（此前只 compile 未 install）。
- 修复：`mvn install -pl jeecg-boot-module/jeecg-module-mail`。启动脚本本身无需改。

## 3. 关于“同步看起来卡住”的说明

首轮观察 18 秒内 running 恒为 true，曾按 ❌ 即停排查。核实后确认**不是缺陷**：

- 索引持续增长（41→66），last_uid 正常写入（Inbox 3239、Sent 9）
- 卡住原因是 QQ 邮箱 Inbox 有 60 封、且 `upsertIndex` 为逐封 `selectOne + insert` 的 N+1 写法
- 最终在约 40 秒内完成

**性能风险（非阻塞）**：N+1 在邮件量大时会线性放大。建议二期改批量 upsert（`insert ... on duplicate key update` 或先批量查已有 uid 再分批插）。当前 66 封耗时约 40 秒，若单账号上千封会到分钟级。
