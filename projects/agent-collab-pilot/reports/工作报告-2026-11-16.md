# Agent Collab Pilot — 项目设计与进展报告

**项目名称**：Agent Collab Pilot — AI 集群团队协作效率工具（试点）
**报告日期**：2026-11-16
**当前阶段**：W1 底座建设（架构设计已冻结，基础设施已就绪）
**部署目标机**：云虚拟机 VM-14-0-ubuntu（腾讯云 4C/8G，中心代理节点）

---

## 一、项目概述

### 1.1 一句话定义

以 JeecgBoot 为 RBAC 底座，构建 **IM 工作台（类微信/TIM 消息机制）+ 账号池执行层（隔离浏览器登录 webAI）+ Agent 注册调度（Nacos）** 的一体化 AI 集群团队协作系统。云端存储用户关系与设备准入状态，客户端存储会话内容并前置合规审计。

### 1.2 试点定位

小型化实验，用于 AI 集群团队协作效率工具的开发试点。预期对 jeecg 前后端进行删改，实现工具工作台与聊天工作台面板切换；服务器端存储用户关系与登录设备准入状态；客户端承担内容合规审计与会话内容存储管理。成员可通过代理服务器记录与同步跨号 session 复用、消息同步、Agent 发现与注册。

## 二、总体架构

### 2.1 分层视图

```
┌─ 客户端 (桌面端 Tauri/Electron 倾向) ──────────────────┐
│ 双面板: [工具工作台] ⇄ [聊天工作台]                     │
│ 本地: SQLCipher 会话存储 + 合规审计器(规则前置)          │
│ 设备密钥对 + 指纹 + Tailscale 节点公钥 → 上报          │
└──────────────┬─────────────────────────────────────────┘
               │ WSS (消息推送 + 指令 + sync 拉取) / Tailscale 内网
┌──────────────▼─────────────────────────────────────────┐
│ 接入网关 (Spring WebSocket, 单机试点)                    │
│  设备准入校验 → 签发 user+device 绑定 token              │
│  在线状态 (Redis)                                        │
├────────────────────────────────────────────────────────┤
│ 业务服务 (jeecg-boot 删改底座)                           │
│  保留: sys_user/role/permission/字典/菜单               │
│  手写模块: im / agent-task / device / account / audit   │
├────────────────────────────────────────────────────────┤
│ 注册中心: Nacos (临时实例 + MCP registry)               │
├────────────────────────────────────────────────────────┤
│ 执行层: 隔离浏览器池 + 调度 worker                       │
│         (注册为 kind=browser-pool 的 agent 实例)         │
└─────────────────────────────────────────────────────────┘
         MySQL 8 (分片友好 schema) + Redis (状态/发号)
```

### 2.2 三域划分（控制面 / 数据面 / 执行面）

| 域 | 组成 | 职责 |
|---|---|---|
| **控制面** | gateway(9999) + nacos(8848) | 谁能进、流量怎么走；设备准入校验、路由、服务注册 + agent registry + MCP registry |
| **数据面** | system-cloud(7001) + 手写 im/account/audit 模块 | 业务状态；RBAC 底座承载所有权限体系 |
| **执行面** | browser-pool 容器 + worker 进程 + MCP server | 跑任务的实体，全部以 agent 身份注册进 Nacos |

三者只通过 Nacos 注册发现 + REST/WSS 交互——执行面整体可平移到其他节点（控制面/数据面分离原则）。

### 2.3 关键架构决策（七条，不可违背）

1. **消息机制**：写扩散 + 每人 inbox 独立游标（TIM 式），离线补拉靠游标，不引消息中间件
2. **人机协作原语**：一账号一容器；人工 VNC 登录与自动化 CDP 共用同一 `--user-data-dir`，会话锁强制互斥
3. **注册与调度分离**：注册中心 = Nacos（临时实例 + metadata 携带 capabilities）；任务抢占 = agent_tasks 原子 UPDATE 租约。两者绝不合并
4. **合规审计**：客户端执行、HMAC 签名上云，服务器验签不验内容；audit 未过消息禁入 AI 会话
5. **内容边界**：内容存客户端（SQLCipher），云端只存关系/准入/审计结果
6. **分片友好**：schema 无 DB 自增依赖（seq 全 Redis INCR），热表显式分片键，MyCat2 路线
7. **零公网暴露**：内网服务只监听 Tailscale 网卡（100.x），安全组不可自管，无任何公网入站端口

### 2.4 安全边界

- 消息**内容**与**会话存储**：客户端侧（SQLCipher 加密）
- 用户**关系**、**设备准入状态**、审计**结果**（HMAC 签名）：云端
- 服务器不掌握明文内容，但凭签名执行策略（audit 未通过的消息禁止路由进 AI 账号会话）
- 内网服务零公网暴露；noVNC/CDP/管理面板同规则

## 三、核心子系统设计

### 3.1 IM 消息机制与多端同步

**数据模型**（写扩散，每人独立游标）：

| 表 | 职责 |
|---|---|
| conversations | 会话（单聊/群聊），last_msg_id |
| conv_members | 成员关系 + last_read_seq（已读回执） |
| messages | 消息体（uuid + conv_seq + audit_status + recalled） |
| inbox | 每人一份收件箱，seq 由 Redis INCR 发号 |
| devices / device_sessions | 设备注册与会话令牌 |

**同步协议**（WSS 帧）：

```
client → server: connect {device_token}
server → client: hello {user_seq: 当前最新}
client → server: sync {since: 本设备 last_seq}        -- 补漏
server → client: batch {msgs[]} + 新游标
此后 server 实时 push {msg}; 客户端按 uuid 幂等去重
```

- **多端同步**：每设备记 last_sync_seq，重连先拉后推
- **已读回执**：last_read_seq 单调推进，天然支持群聊部分已读
- **撤回**：tombstone 标记 + 内容清空 + 推送更新
- **删除**：仅本端墓碑（inbox.deleted），服务器漫游不受影响
- **离线消息**：游标之后的 inbox 行即离线队列，不引单独中间件
- Redis 职责仅两个：在线状态、seq 发号

**设备准入**（类微信"登录设备管理"）：

1. 客户端生成密钥对 + 指纹 + Tailscale 节点公钥，申请注册 → pending
2. 管理员批准（试点可自动批准）
3. WSS 握手：证书挑战 → 校验 sys_user 凭据 + device 状态 → 签发 user+device 绑定 token
4. 吊销即断连；设备列表页可远程踢出
5. 网络层（tailnet ACL 粗粒度）与应用层（握手细校验）各管各的

**合规审计**（客户端执行，签名防绕过）：

- 审计在**客户端**执行：block 级消息不进发送管道，flag 级标记随消息上云
- 审计结果携带**客户端密钥 HMAC**，服务器验签不验内容——无内容也能执行策略
- 试点规则：关键词 + 正则 + 身份证/手机号模式；模型分类器留接口后补

### 3.2 账号池与隔离浏览器

**核心原语**：一账号一容器。人工与自动化**共用同一 profile 目录**，靠**会话锁**互斥：

- 人工经 VNC/noVNC 手动登录 webAI（登录态落盘持久化）
- 自动化经 CDP（Playwright `connect_over_cdp`）复用会话执行任务
- 任一时刻只允许一侧持有会话锁；调度器负责仲裁与通知

**容器镜像**（自研，debian:bookworm-slim + chromium + openbox + x11vnc + xvfb + supervisor）：

```dockerfile
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y \
      chromium openbox x11vnc xvfb supervisor
# supervisord 拉起: Xvfb → openbox → x11vnc(:5900) → chromium
# chromium 关键启动参数:
#   --remote-debugging-port=9222
#   --user-data-dir=/data/profile    # Chrome 136+ 必须非默认目录才允许 CDP
#   --proxy-server=...               # 按账号注入独立代理(可选)
VOLUME /data        # 挂 ./pool/<账号ID>/ 宿主机目录, cookie 跨重启存活
EXPOSE 5900 9222
```

注：自研原因是 KasmVNC 系镜像协议私有，无法接入经典 VNC 网关。`--user-data-dir` 指向唯一 profile 目录使人工登录与 CDP 自动化共享登录态；两侧同时启动会因 SingletonLock 冲突，会话锁是硬约束。

**账号生命周期状态机**：

```
provisioned → needs_login → healthy ⇄ in_use → (风控/过期) → needs_login
                  ↑________________人工登录_________________|
```

**出口 IP 与风控**：同机容器共享服务器公网 IP，平台做 IP 维度关联风控时一损俱损。缓解：每容器注入独立代理（静态住宅 IP）。这只降低账号间关联，不等于合规——webAI ToS 普遍禁止多账号/会话共享，账号按可消耗资源设计，状态机含 dead。

**资源估算**：每 Chromium 实测 0.5–1GB RAM。4C8G 起步可扛网关 + 10 左右容器；池子扩大走横向扩。

### 3.3 Agent 注册发现与任务调度

**注册中心：Nacos**（2026-11-14 决策，替代自研注册表）

- 业务微服务：Spring Cloud Alibaba 原生注册
- 浏览器池 worker（Python/Node）：nacos sdk 注册**临时实例**，心跳由 Nacos 托管，进程消失自动摘除
- **capabilities 放 instance metadata**：`capabilities=web-chatgpt:2,claude-web:1`，发现侧按标签过滤 + 订阅变更推送
- **Nacos3 MCP registry**：MCP 类 AI 工具直接注册，工作台作为 MCP client，省一半自研协议工作量
- Agent registry 独立 group `AGENT_GROUP`，与 jeecg 业务服务隔离

**任务调度：agent_tasks 租约表**（MySQL，不并入 Nacos）

Nacos 不管任务语义，抢占必须自己保证：

```sql
UPDATE agent_tasks
SET agent_id = ?, status = 'claimed', lease_until = NOW() + INTERVAL 120 SECOND
WHERE id = ? AND status = 'queued';
-- 影响行数=1 才算抢到
```

worker 运行期心跳续租；lease_until 过期由清扫器重排回 queued。这是集群不重复执行的唯一保障。

**人机协作闭环**：

```
任务入队 → worker 抢占(某 webAI 账号) → CDP 执行
   ↓ 命中登录失效/风控/验证码
账号标记 needs_login → 释放锁 → 通知人工
   ↓ 人工经门户 VNC 重登 → 巡检恢复 healthy
任务重新入队执行
```

人工不是调度系统的例外，是状态机里的一个标准环节。

**负载均衡（试点简版）**：worker 心跳上报 load_score，调度器选 healthy 账号里负载最低的实例。

## 四、基础设施与组网

### 4.1 组网方案（Tailscale）

**核心约束**：服务器安全组由云服务商持有，无法开放任何公网入站端口。

- 自建 WireGuard（需入站 UDP 51820）→ 不可行
- Tailscale 打洞 / DERP 中继，零入站端口 → 唯一可行解

**当前状态（2026-11-16）**：

| 节点 | Tailscale IP | 状态 |
|---|---|---|
| vm-14-0-ubuntu（本服务器） | 100.78.65.37 | 在线 |
| rog-x（Win11 主力机） | 100.97.76.85 | 在线 |
| honor-70pro（Android） | 100.101.26.38 | 离线（1 天前） |

组网已通，双通 SSH 已验证（服务器 ↔ rog-x 免密互连）。

### 4.2 端口矩阵（tailnet 内可达）

| 端口 | 服务 |
|---|---|
| 80 | jeecg 前端 (Nginx) |
| 8080 | jeecg-boot API（单体，当前形态） |
| 9999 | gateway（微服务形态入口） |
| 7001 | system-cloud（微服务形态） |
| 13306 | MySQL |
| 8066 | MyCat2 统一数据库入口 |
| 8848 / 9848 | Nacos 3.2（HTTP / gRPC） |
| 18080 | Nacos 控制台 |
| 7890 | Clash mixed 代理出口 |

### 4.3 代理出口（Clash/mihomo）

GLaDOS 订阅已接入（Basic 400 天，有效期至 2027-12-19，总流量 200 GiB）。33 个节点、5 个策略组（GLADOS-AUTO / POOL-JP / POOL-SG / POOL-US / GLOBAL）。Google 等境外站点实测可达。浏览器池账号的独立代理出口预留：容器 `--proxy-server` 指向 Clash mixed 端口。

### 4.4 Jeecg 微服务价值评估结论

采用四维打分 + 一票否决制（直接价值 / 架构契合 / 成本 / 可恢复性）：

| 裁决 | 模块 | 理由 |
|---|---|---|
| ✅ 开启 | gateway(9999) | 控制面门面，统一入口，设备准入校验挂载点 |
| ✅ 开启 | system-cloud(7001) | RBAC 地基，所有手写模块权限挂此 |
| ❌ 关闭 | demo-cloud | 零价值纯攻击面 |
| ❌ 关闭 | rabbitmq | 架构一票否决：已定写扩散+inbox 游标 |
| ❌ 关闭 | sentinel / monitor / seata / shardingsphere | 试点无流量/无分布式事务需求 |
| ⏸ 候选 | xxljob / pgvector / sharding.yaml | 价值真实但不在 W1-W2 关键路径，启用条件明确 |
