# Flowable 工程化实战：从嵌入式单体到分布式治理

## 一、先做架构决策：嵌入式、集中式，还是领域自治

这是所有后续设计的起点。选错部署形态，后面的分布式问题会成倍放大。

Flowable 引擎本质上是一组**可嵌入 Java 应用的引擎与服务 API**，Spring Boot 自动配置会创建 `ProcessEngine` 并把 Repository / Runtime / Task / History 等服务注册为 Bean。三种形态的适用边界如下：

**嵌入式单体**：Flowable 与业务模块在同一个 Spring Boot 进程中。一次“提交申请”可以在同一个 `@Transactional` 里完成业务单据更新、流程实例启动和待办创建，业务表与流程表共享本地事务，回滚即整体回滚。这是大多数审批、OA、中后台系统的首选——调用链短、一致性简单、调试方便。它不是“玩具模式”，而是 Flowable 的一等使用方式。

**集中式流程服务**：Flowable 独立部署，通过 REST 或消息为多个业务系统提供流程能力。适合流程模型需要跨团队复用、但业务事务边界仍然清晰的场景。代价是引入远程调用超时、序列化和网络故障这些新的失败模式。

**领域自治流程服务**：每个业务域拥有自己的 Flowable 实例、模型和数据库，跨域流程通过事件或受控 API 协作。只有“业务边界稳定、团队能独立交付、流程负载需要独立伸缩”三个条件同时成立时，微服务化才有明显收益。如果只是担心单机故障，增加同构节点和数据库高可用就够了，不必拆服务。

一个容易忽视的集群事实：多个 Flowable 节点共享同一个数据库就自动形成集群，不需要节点间缓存同步等额外机制。**集群 ≠ 微服务**——水平扩容得到的是一个逻辑流程服务，并不等于按业务域完成了拆分。

> **决策速查**：审批为主、团队规模有限、一致性要求高 → 嵌入式单体。流程需要被多个异构系统复用、且业务事务边界清晰 → 集中式流程服务。只有在三个条件同时满足时才考虑领域自治，否则先做模块化。

## 二、微服务分布式一致性：最终一致 + 补偿，而不是分布式事务

工作流场景**不适合把多个数据库包进一个长事务**。流程引擎自身有本地事务保障，但跨服务的业务一致性需要应用层来兜底：业务侧通过“终态事件 + 幂等 + 补偿 Job”对齐状态。

### 2.1 双状态模型与关联字段

流程状态和业务状态必须显式分离、可对账。核心关联靠 `businessKey` 打通：

| 维度 | Flowable 侧 | 业务侧 |
|---|---|---|
| 关联 | `businessKey` | 业务单 ID |
| 实例标识 | `processInstanceId` | — |
| 审批状态 | 流程变量 / 终态 | `approvalStatus` |
| 业务状态 | — | `applicationStatus` |

一致性保障的关键点：**发起流程和更新业务表放在同一个 `@Transactional` 里**（嵌入式形态下天然可行）；**业务最终状态只跟流程实例终态绑定**（APPROVE / REJECT / CANCEL），不要跟单个 Task 绑定。

### 2.2 补偿机制：BPMN 的 Saga 表达

Flowable 的补偿通过 BPMN **补偿边界事件 + 补偿抛出事件** 实现。每个已完成的服务步骤挂一个补偿边界事件，失败时沿错误路径逐个调用已完成步骤的补偿。补偿通常是一个普通的 Service Task，按**完全相反的顺序**执行。

需要清醒认识：**补偿是 best-effort**。补偿本身失败时，必须有记录机制（`compensationErrors` 之类的落脚点）并让链继续或进入人工处置，不能假设补偿一定成功。幂等、补偿和领域数据一致性始终是应用的责任，引擎不会自动消除外部副作用。

### 2.3 状态回写：跨进程边界后的正确姿势

单体时代用本地 Spring Event 回写业务状态，拆成微服务后 Java 对象调用越过了进程边界。可靠做法是：**引擎监听器监听流程实例的创建、完成、取消事件 → 交给流程实例服务处理 → 通过消息（MQ）投递到业务侧 → 业务侧幂等消费 + 失败重试**。幂等键使用 `processInstanceId + 事件类型`，确保重复投递不产生重复副作用。

## 三、多租户隔离：tenantId 不是唯一答案

Flowable 多租户有三种落地路径，按隔离强度递增：

**共享库 + `tenantId` 行级隔离**：Flowable 默认支持在部署时设置 tenant identifier，查询时按 tenantId 过滤。适合 SaaS 租户量大、数据隔离要求为逻辑隔离的场景。关键安全原则：**tenant_id 必须由后端从 JWT 等可信源解析后注入请求上下文（ThreadLocal 或 `TenantContext`），绝不信任前端传参**。

**每租户独立 Schema**：使用 `MultiSchemaMultiTenantProcessEngineConfiguration`，每个租户拥有自己的数据库 schema，通过 `TenantInfoHolder` 确定当前活跃租户，新增租户通过 `registerTenant(String, DataSource)` 动态完成——**启动后也可以继续注册**。注意此配置下默认 ID 生成器必须使用 `StrongUuidGenerator`，普通的 `DbIdGenerator` 不可用。异步执行器有两种选择：`ExecutorPerTenantAsyncExecutor`（每租户一个完整执行器）或 `SharedExecutorServiceAsyncExecutor`（每租户有获取线程，但作业执行共享线程池）。

**每租户独立引擎**：隔离发生在引擎/部署级别，而不是通过 `tenantId` 字段。此时应让 `tenantId` 保持为空，不要自动回填——否则字段不携带任何信息，反而制造混淆。

**选择原则**：租户数量可控且数据安全要求高 → 独立 Schema 或独立引擎；租户数量大、以逻辑隔离为主 → 共享库 + tenantId，但必须把 tenantId 注入作为基础设施层的强制约束，而不是靠每个查询手动加条件。

## 四、异步执行器与集群：锁、节点亲和性、乐观锁

异步执行器是分布式 Flowable 最容易出生产事故的地方。

**基本机制**：异步作业持久化到数据库，各节点通过**乐观数据库锁**竞争获取作业；一个节点获得锁后独占执行，其他节点不会重复抓取。这意味着 Flowable 集群不需要节点间的作业协调——数据库就是协调者。

**节点亲和性（Node Affinity）**：请求进入的节点会优先尝试在本节点调度异步作业，再交给其他节点。这是默认行为，在多数场景下有利于减少跨节点延迟。

**集群下最常见的配置陷阱——节点“囤积”作业**：在 Flowable 7.2.0 中观察到的一种行为是，Node 1 把自己 `LOCK_OWNER_` 下的每一个作业都锁住，即使实际只能处理少量，其余作业无法被 Node 2 获取。修复方式是将线程池配置从 `flowable.process.async.executor.*` 切换为 Spring 的 **`spring.task.execution.pool.*`** 属性。如果使用集群，务必检查这一项。

**乐观锁异常**：并行分支在汇聚点、或多个执行器竞争同一流程实例时，可能出现 `FlowableOptimisticLockingException`。缓解手段包括：保持各节点异步执行器配置一致；合理调大 `asyncExecutor` 锁时间并调小每轮获取数量，降低多节点同时抓同一批作业的概率；清理已经不存在对应流程实例的陈旧作业。默认的 **exclusive job** 会将同一流程实例的异步工作串行化，本身就是在降低这类冲突。

**部署锁**：集群启动时每个节点默认都会独立执行 classpath 自动部署。如果需要确保只有一个节点部署，开启：

```
flowable.auto-deployment.use-lock=true
flowable.auto-deployment.lock-wait-time=PT5M
```

其他节点会等待锁释放。

## 五、历史数据与查询性能：不要等表大了才治理

历史表膨胀不会让每次审批都直接扫描历史表，但历史写入会占用事务、日志、缓存和 I/O，历史查询和批量删除会与运行时审批**争抢数据库资源**，这才是线上“审批变慢”的真实传导路径。

一套可持续的治理分四层，而不是一次 DELETE：

**第一层，控制历史级别的“精度”**。将 `history-level` 设为满足审计需求的最低级别。如果只需要活动轨迹而不需要每次变量更新的明细，就不要用 `full`——`ACT_HI_DETAIL` 的增长速度会比业务数据快一个数量级。

**第二层，在线查询必须有边界**。所有历史/待办查询强制分页，禁止无界 `list()`。对于高频、多状态的待办列表，**不要直接查 `ACT_RU_TASK` 做复杂过滤**；业界更稳妥的做法是设计一张专用的“待办/已办”业务表，由引擎事件驱动同步写入，查询走业务表而非 Flowable 原生表。如果确实需要复杂关联查询，`createNativeTaskQuery()` 可以做原生 SQL，但必须带 `listPage` 且 WHERE 条件有可用的索引支撑。

**第三层，按流程类型建立分级保留策略**。高频低价值流程（如简单的状态流转）保留较短周期，核心审批保留较长周期。Flowable 内置的 history-cleanup 作业可以按保留期**小批量**删除已完成实例，不要用一次性大事务直接 DELETE。

**第四层，冷热分离与分区**。超过在线保留期的历史数据迁移到归档库；对 `ACT_HI_*` 大表按时间维度做表分区，利用分区裁剪减少查询 I/O。

**如果只能先做三件事**：统计各历史表和索引的增长速度；用慢 SQL 定位真正影响审批链路的查询；选一个低风险流程在非高峰期小批量试跑清理。

## 六、Spring Boot 工程配置清单（生产向）

以下配置项在微服务/集群部署中需要显式确认，而非依赖默认值：

| 配置 | 生产建议 | 原因 |
|---|---|---|
| `flowable.database-schema-update` | 生产设 `false`，用 Flyway/Liquibase 管理 DDL | 避免多节点启动时并发改表 |
| `flowable.async-executor-activate` | 需要定时器/异步任务时必须 `true` | 否则定时器永远不触发 |
| 异步线程池 | 集群下优先使用 `spring.task.execution.pool.*` | 规避节点囤积作业问题 |
| `flowable.auto-deployment.use-lock` | 集群设为 `true` | 防止多节点同时自动部署 |
| `history-level` | 按审计需求取最低可用级别 | 直接控制历史表增长速度 |
| 流程定义 Key | 一旦投产**不变**，变更走版本号 | 避免运行中实例错配 |
| 数据源 | 考虑引擎与业务双数据源隔离 | 避免引擎表负载干扰业务表，提升安全性与处理效率 |

**版本兼容是硬约束**：Flowable 7.x 要求 JDK 17+ 和 Spring Boot 3.x；Flowable 8.0.0 已升级到 Spring Framework 7 / Spring Boot 4。如果现有技术栈是 Spring Boot 2.7，应选择 Flowable 6.x 系列，不要在版本适配上“先跑起来再说”。

## 七、速查：微服务分布式场景下“不要做什么”

- **不要**把多个微服务的数据库包进一个 Flowable 长事务——用最终一致 + 补偿。
- **不要**假设补偿一定成功——补偿是 best-effort，必须有失败记录和人工处置路径。
- **不要**在微服务拆分后继续依赖进程内 Java 事件回写业务状态——越界后走消息 + 幂等消费。
- **不要**信任前端传入的 `tenantId`——必须由后端从可信身份上下文中注入。
- **不要**在集群中混用 `flowable.process.async.executor.*` 和 `spring.task.execution.pool.*`——先用后者排查作业囤积问题。
- **不要**直接对 `ACT_HI_*` 大表做无界查询或大事务 DELETE——分页、小批量、分级保留。
- **不要**在 Flowable 6.x 与 7.x/8.x 之间仅凭“API 看起来一样”就迁移——JDK、Spring、事务管理、SQL 方言均有显著差异。


**最后一条选型提醒**：如果流程的核心特征变成“跨多个服务、长时间运行、以代码为中心、故障后必须可靠恢复”，而人工任务和 BPMN 可视化不再是主导，那么需要认真评估的不再是“怎么把 Flowable 配得更好”，而是执行模型是否匹配——Temporal 的持久化执行模型在这种场景下比基于关系数据库轮询的 BPMN 引擎更合适；但无论用哪个引擎，幂等、补偿和领域数据一致性仍然是应用的责任。
