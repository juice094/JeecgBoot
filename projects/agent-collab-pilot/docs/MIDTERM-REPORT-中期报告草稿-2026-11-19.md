## 2. 业务设计：两个模块怎么编排（3 分钟）

[屏幕：任务状态机图 + 审批链时序 + audit_log 事件表]

- **任务状态机**：六条流转全合法、done 非终态；流转只走一个端点，`/edit` 服务端回填状态堵旁路。
- **权限四层**：认证（Token）→ 授权（按钮权限）→ 确权（service 层归属校验）→ 审计（audit_log 只增不改）。**前端隐藏按钮不算安全，闸门全部收敛在服务端**。
- **事件流**：不建独立事件表，复用 audit_log（与 GitHub events 同构），一次写入服务两个视角。

（口径：这部分讲"为什么这么设计"——GitHub 是参照系不是拍脑袋；每个取舍都写了已知代价。）

## 3. 决策方法论：Flowable 线的一个完整样本（3 分钟）

[屏幕：决策链五步图]

1. **实证起点**：发现此 fork 已裁掉上游 platform 线——"平台自带 Flowable"的假设当场死亡；
2. **兼容性查证**：官方 release note + Maven Central POM 双证据锁定 Flowable 8.0.0 = Spring Boot 4 线（7.x 全线不兼容）；
3. **尖刺验证**：最小流程在本 fork 真实启动建表（39 张），成本最小化验证；
4. **骨架落地**：`jeecg-module-flow` 模块按"未立项骨架不进运行时"的仓库先例注册；
5. **W1 闭环**：接线 system-start + 8083 冒烟四验证 + 端口纪律（在役 8081 零触碰）。

（口径：这是全场最重要的一节——讲的不是 Flowable，是**我们怎么做技术决策**：假设必查证、重器先尖刺、副作用显式声明、每步留可复验证据。中段答辩被追问"为什么这么选"时，把这一节的方法论抽象出来回答。）

## 4. 治理基座：让 agent 协作可控（4 分钟）

[屏幕：五原语架构图（简化版）+ 三个漂移案例]

- **问题**：单人 + 少量 agent 的真实场景里，我们一天内踩了三个坑——模型别名漂移（K2.8/K3）、思考档位漂移（max 烧 token）、配置被另一运行时回退。共同模式：**政策引用了承载层未登记的能力**。
- **对策**（五个原语，file-based 零依赖）：规则分层单源 / 能力目录（政策只许引用目录 id）/ 派工契约（规则随契约走不随会话走）/ 统一身份底座 + agent 四增量 / 漂移检测即代码。
- **成效（当天实证）**：目录外别名 → 工具层物理不可选；max 默认档 → 检测器报警；config 回退 → 被抓现行。

（口径：这节是金句区——"**能约束 agent 的规则体系，同样约束人**"；"身份底座唯一：agent 注册为 sys_user 的一种类型，人类的每一道闸门自动成为 agent 的闸门"。）

## 附：备用问答（预判三个最可能被问的问题）

**Q：Flowable 为什么不一开始就用？** → 当时目标函数是试点最小化学习面；目标函数变了（多流程类型 + agent HITL），且迁移成本随数据量增长是凸函数——越拖越贵，所以 NOW。历史决策是证据不是终审。

**Q：agent 治理是不是过度设计？** → 三个漂移案例都是今天真实发生的，其中别名漂移直接导致一次无效委派。治理基座的全部代码是 2 个 Python 脚本 + yaml，单人可运维——防的是"政策与现实脱钩"这一类必然复发的问题。

**Q：和直接用现成多智能体框架的区别？** → 编排玩具解决"怎么派活"，我们解决"派出去的活凭什么可信"——四层确权、契约承载、漂移检测，这些在 CrewAI/Swarm 类框架里不是一等公民。
