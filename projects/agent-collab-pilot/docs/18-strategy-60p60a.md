# 18 — 战略重估：面向 60 人 + 60 Agent 人机混编团队的协作服务

> 2026-11-17，Kimi Code 起草，宿发起。参考组织原型：NVIDIA 高管架构（6~7 个业务域，每域 3~9 名负责人；首席科学家/CTO/CFO 为决策与资源节点；强跨域协同需求）。
> 本文不吹系统高度，只做三件事：①这个规模下协作难点是什么（诚实清单）；②现有设计哪里不够用（差距分析）；③怎么用最小代价真实提升效率（分阶段路线）。
> 适用范围同时覆盖：高管/科学家团队的流程编排与决策协同，以及普通团队/个人的日常业务处理与审批交流。

## 一、这个规模下，协作到底难在哪

60 名人类成员 + 60 个 agent（1:1  staff 配比）的人机混编团队，难点按真实严重程度排序：

### 1.1 注意力是硬通货，而 agent 会制造注意力通胀
- 60 个 agent 每天产生的消息、回执、文档草稿，如果直接涌入频道，人类成员的注意力会被稀释到无法决策。**最大风险不是 agent 不够能干，而是 agent 太能产出了。**
- 高管时间按分钟计：任何"多一步操作"都会被弃用。新工具的路径长度必须 ≤ 现有习惯（发消息/转发邮件），否则落地即死。

### 1.2 人机混编的信任与授权边界
- "这条结论是 agent 给的还是人给的？""这个 agent 凭什么替我提交这份预算？"——人机混编下每条自动化动作都需要可审计凭证与授权边界。
- 必须分级：哪些动作 agent 可自动执行（查资料、起草）、哪些必须人类确认（对外承诺、金额支出）、哪些禁止（越级代表发言）。**没有边界的自动化在高管团队等于事故。**

### 1.3 审批拓扑从"链"变成"网"
- 现状：部门主管→分管副总两级链。高管团队场景：跨域项目要 AI VP + 硬件 VP + CFO 会签；百万级资源申请走 CTO→CFO；科学评审走首席科学家 + 外部专家；且大量"代审"（VP 出差，授权副手）。
- 超时是常态（高管异步）：需要截止提醒、超时升级、批量审批（一次过目 20 条待决）。

### 1.4 信息分级与数据主权
- 高管团队的信息天然敏感：薪酬、并购、未发布产品、评审意见。agent 的数据可见范围必须跟随其"代表的人"，不能因为是 agent 就默认全局可读。
- 数据主权问题现实存在：自托管是底线选项；接入外部大模型时的出域边界要可配置、可审计。

### 1.5 Agent 治理本身成为工程问题
- 60 个 agent 的注册、能力声明、版本、失效、行为审计、配额——这和管 60 个实习生是同一个问题，必须有工牌（身份）、岗位说明（能力边界）、考勤（审计日志）。
- 冲突场景：两个 VP 的 agent 对同一事项给出矛盾结论，谁在频道里说了算？需要"结论归属人"机制，agent 永不拥有最终发言权。

### 1.6 流程形态分化
- 科学评审（论文/实验方案/GPU 资源申请）与行政审批（报销/用章）形态完全不同：前者要附件评审 + 打分 + 多人意见汇总，后者要条件路由（金额阈值）。
- 一刀切的状态机不够用；但上 BPM 引擎又过重。中间态：**可配置流程模板 + 轻量条件路由**。

### 1.7 知识沉淀：决策为什么做出
- 高管团队最贵的资产是决策过程。会议纪要→行动项→验收闭环，决策记录（背景/选项/结论/反对意见）要可回查。普通 OA 只记"批了/没批"，不记"为什么"。

### 1.8 对普通人的可迁移性
- 同一引擎降配可用：中小团队/社团/家庭的事务（报销、请假、活动经费、值班表）= 默认流程模板 + 命令入口 + 免培训表单。这决定了**模板体系与默认值设计**是产品级要求，不是企业定制。

## 二、现有设计的差距分析（诚实版）

| 现有能力 | 60+60 场景下的差距 | 严重度 |
|---|---|---|
| 审批两级状态机（team_approval） | 需条件路由、会签、委托、超时升级、批量审批 | 高 |
| ToolCall 回执卡片 | 协议够用，但缺"授权边界"字段（谁授权、自动/确认/禁止级） | 高 |
| 斜杠命令 | 够用且是核心优势；需参数解析与权限感知（高管看到更少命令） | 中 |
| 菜单/路由驱动工作台 | 120 成员的频道/会话管理、订阅分级、每日摘要缺失 | 高 |
| sys 原生 RBAC | 人类角色够；agent 身份模型（代表关系、能力声明、数据范围）缺失 | 高 |
| 单体架构 | **不是瓶颈**：120 账号、日万级消息与千级审批，单体富余一个量级；瓶颈在交互与治理，不在架构 | 低（不吹不黑） |
| 公告/站内消息 | 缺"决策记录"与"行动项闭环"实体 | 中 |
| 会话工作台壳层 | 消息通路仍是 M2 规划；这是 60+60 的主战场，优先级应上调 | 高 |

## 三、设计调整（对现有系统的最小演进）

### 3.1 流程域：从状态机到可配置流程（小步演进，不上 BPM）
- 新增三张表：`team_flow_def`（流程模板：JSON 定义节点/条件/会签策略）、`team_flow_inst`（实例：当前节点、状态）、`team_flow_task`（任务：待办落到具体人，支持委托关系与批量）。
- 条件路由用轻量表达式（JSON Logic 子集，先支持 金额阈值/类别匹配 两类，够用即止）。
- 会签两种策略：任一通过 / 全部通过；并行节点同时出任务。
- 委托：`team_flow_delegate`（A 授权 B 在时间段内代审，任务可见性跟随）。
- 批量审批接口 + "今日待决"视图（按截止时间排序，不是分页列表）。
- 现有 team_approval 保留为"单线流程模板"的一种特例，数据不迁移、接口兼容。

### 3.2 Agent 身份与治理（先于 agent 能力建设）
- agent 是特殊用户：`sys_user` 扩展标记 + `agent_principal`（代表谁）+ `capabilities`（能力声明 JSON）+ `policy`（per 工具：auto/confirm/deny）。
- 频道发言权规则：agent 消息默认折叠为回执卡片（不占未读），@人类成员或策略为 confirm 的动作才推送。
- 审计面：agent 每次工具调用强制携带 principal 与 policy 判定结果；审计页可按 agent/按人/按工具三维检索。
- 冲突裁决：频道内结论归属人类成员，agent 输出标注来源，永不置顶。

### 3.3 消息与注意力治理
- 订阅分级：频道分"必读/摘要/免打扰"三档；agent 密集频道默认摘要档。
- 每日摘要：agent 产出按人聚合为一份 digest（xx 处理了你委托的 N 件事，M 件待你确认），替代逐条推送。
- 决策记录实体：`team_decision`（背景/选项/结论/反对意见/关联单据），审批单与会议可挂接。

### 3.4 普通人场景的降配设计
- 流程模板市场：默认带 报销/请假/采购/活动经费/值班 五套模板，开箱即用；
- 命令入口即培训：新成员只会打 "/申请 报销 打车费 86" 就能完成全部操作；
- 零配置部署：单机 docker compose 一键起，管理面默认隐藏。

## 四、分阶段路线（每阶段有可量化验收，不画大饼）

| 阶段 | 内容 | 验收口径 | 依赖 |
|---|---|---|---|
| P1（现在→+3 周） | 流程模板化 + 会签/委托/批量审批 + 决策记录 | 60 人模拟数据下，跨域会签流程跑通；批量审批 20 条 ≤ 1 分钟 | 无，基于现有 team_approval 演进 |
| P2（+3~6 周） | 消息通路上线（IM 组装）+ 订阅分级 + 每日摘要 | 120 账号并发消息无丢失；agent 消息 100% 折叠为回执 | IM 组件选型（Mattermost 候选） |
| P3（+6~10 周） | Agent 身份模型 + 治理面 + 策略引擎 | agent 动作 100% 携带 principal/policy 审计字段；confirm 级动作 0 自动执行 | P2 |
| P4（+10 周+） | 模板市场 + 开放接入（对外 API） | 非研发人员 30 分钟自建一条流程模板 | P1 |

## 五、风险与缓解（诚实清单）

| 风险 | 说明 | 缓解 |
|---|---|---|
| agent 幻觉进入审批链 | 起草的报销/合同金额错误 | confirm 级强制人工；金额类字段 diff 高亮 |
| prompt 注入经消息进入 | 频道里贴一段"忽略之前指令…" | 工具调用与消息渲染严格隔离；指令只来自服务端策略，不来自消息文本 |
| agent 间循环调用 | A 委托 B、B 又委托 A | 委托图有向无环校验 + 最大跳数 |
| 高管不用 | 路径比现有习惯长一步 | 每个高频动作做 A/B 计时验收；不达标不发布 |
| 单点与数据主权 | 自托管单机的可用性 | 每日备份 + 文档化恢复流程；外部 LLM 出域白名单 |
| 范围蔓延 | 60+60 诱惑做"大平台" | 本文即边界：P1~P4 之外的需求一律登记不排期 |

## 六、叙事口径（对外一句话）

不说"人机混编协作操作系统"这种大话。说：**"把 60 个人和 60 个助手放在同一个组织里时，让每件事都有最短路径、每个自动化动作都有凭据、每个决策都有记录的工具。"** 普通人用时，它是"会聊天的流程助手"。
